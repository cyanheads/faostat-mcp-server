# faostat-mcp-server — Design

Global food and agriculture statistics from the UN's [FAOSTAT](https://www.fao.org/faostat/) — crop and livestock production, agricultural trade, food balances, food security, land use, fertilizer/pesticide use, and agri-emissions, for 245+ countries from 1961 to present.

Data path: FAOSTAT's keyless **bulk-download service** (per-domain zipped normalized CSVs), synced into a persistent local **MirrorService** (embedded SQLite + FTS5) and queried locally. The public REST query API requires authorization (401 keyless — see [Design Decisions](#design-decisions)), so the mirror is the data path, not an optimization. Analytical query results spill to a **DataCanvas** for ad-hoc SQL.

## Overview

**What it wraps:** FAOSTAT — the FAO's authoritative global food & agriculture statistics, organized into ~68 *domains*. Each domain is a cube of **area** (country/region) × **item** (commodity) × **element** (metric: production, yield, area harvested, import/export quantity & value, …) × **year**, with a data-quality **flag** per observation.

**Data acquisition:** FAOSTAT publishes the full corpus as keyless per-domain ZIPs (normalized long-format CSV + bundled dimension code lists). The server syncs a **selected set of domains** into a local SQLite mirror on a schedule and serves every query from the mirror — fast, offline-capable, no per-request rate limits. The (auth-gated) REST API is not used.

**Audience:** Economists, food-security and development researchers, journalists, sustainability analysts, and agents answering production/trade/consumption questions at country and global scale. Composes with `worldbank-mcp-server` (development indicators alongside ag production), `usda-mcp-server` (US detail vs. FAO's global view), `eurostat-mcp-server` (EU cross-check), `gbif-biodiversity-mcp-server` (crop/species context).

**Scope:** Read-only. The corpus is published reference data; there are no writes, no irreversible operations. The only state the server owns is its local mirror (a derived cache of public data, rebuildable from source) and ephemeral per-session canvases.

## Requirements

- **Keyless.** No API key — the bulk service is public. `auth: none`.
- **Local mirror as primary data path.** Sync selected domains' bulk CSVs into embedded SQLite (one table per domain, plus shared dimension tables); query the mirror, never the live REST API per request.
- **Code resolution is mandatory.** Area and element codes are integers; item codes can also be alphanumeric. `faostat_resolve_codes` returns numeric `code` or exact `code_text` for items, with the other field null. A CPC crosswalk is separate from item identity.
- **Area-code duality must surface.** The `area` dimension mixes individual countries (e.g. Afghanistan=2) and aggregate regions (World, Africa=5100, EU). Observations default to **excluding aggregates** (`include_aggregates: false`) so an agent doesn't sum a region with its members; `resolve_codes` labels each area `country` vs `aggregate`.
- **Data-quality flags carried through.** Every observation has a flag (A=Official, E=Estimated, I=Imputed, B=Time-series break, X=External). Carry it on every row; never drop it — it's load-bearing for rigor.
- **Analytical SQL surface.** Cube queries are inherently `GROUP BY country/item/year` analytical workloads → DataCanvas spillover + a mandatory `faostat_dataframe_describe`/`faostat_dataframe_query` pair.
- **Refresh, don't block startup.** Initial mirror build runs out-of-band (CLI); incremental refresh runs on a schedule. Read path gates on mirror readiness with a clear "still indexing" error when cold.
- **Stream-parse bulk CSVs.** Decompressed CSVs are large (QCL: 33 MB zip → ~600 MB CSV, ~18× ratio). Stream rows from the zip into SQLite; never materialize the full CSV in memory.

A deployment constrained on RAM/disk can drop it from `FAOSTAT_DOMAINS`.

The selection is **config-driven** (`FAOSTAT_DOMAINS`), so the indexed set can grow without code changes. `faostat_list_domains` reads the live manifest for the *full* catalog and annotates which are locally indexed — an agent always sees what exists and what's queryable.

## Services

| Service | Wraps | Used By |
|:--------|:------|:--------|
| `faostat-mirror` | FAOSTAT bulk-download service (manifest `datasets_E.json` + per-domain ZIPs); embedded SQLite mirror via `MirrorService` (`defineMirror`/`sqliteMirrorStore`) | all data tools |
| `ReadPool` (`faostat-mirror/read-pool.ts` + `read-worker.ts`) | Two `node:worker_threads` workers that run cube reads, dimension text search, index preparation and statistics builds off the main thread | `faostat-mirror` |
| canvas accessor | `core.canvas` (DataCanvas, DuckDB) — module-level `getCanvas()` accessor wired in `setup()` | `query_observations`, `commodity_profile`, `dataframe_*` |

**Mirror service shape.** One `MirrorService` instance per indexed domain (each domain is its own table + FTS index over the dimension labels), plus shared dimension tables (`areas`, `items`, `elements`, `flags`) populated from the bundled code-list CSVs, with `items` also taking the identities and labels of data rows whose item the list omits. The `sync` ingester:

1. Fetches the manifest (`datasets_E.json`); for each selected domain compares `DateUpdate` / `Last-Modified` against the stored checkpoint — skip unchanged domains.
2. Streams the domain ZIP, parses the bundled code-list CSVs into the shared dimension tables, then stream-parses the normalized data CSV → row objects keyed by the declared columns. Each row stamps `file_date_update`, its file's `DateUpdate` as Unix epoch seconds, and the item identities the rows name that the ZIP's item list lacks join the item vocabulary under the label of their first row; a list entry always wins over a row-derived one.
3. Yields pages of `{ records }`, then `{ records: [], tombstones }`, the last page carrying `checkpoint: DateUpdate`. `checkpoint` is the domain's ISO `DateUpdate` (lexicographically monotonic); no intra-run `cursor` needed (a domain ZIP is one atomic unit — re-fetch on interrupt rather than resume mid-file). After the last data page, the ingester reads the ids of rows not stamped with this file, in bounded rowid slices on the read pool, and yields them as tombstones; the last removals ride the page that carries the checkpoint, so none follows it. A manifest `DateUpdate` that is not a `YYYY-MM-DDTHH:MM:SS` instant stamps no rows and removes none, with one warning; the next file with that form removes what it does not carry. A data file that yields no data row, such as one holding only its header (FAO has shipped one), removes none and completes with its checkpoint, with one warning, since a publishing fault is not the withdrawal of a whole domain; the next file that carries rows removes what it does not carry.

**Schema (per-domain table):** `area_code INTEGER, area_m49 TEXT, area TEXT, item_code INTEGER, item_code_text TEXT, item TEXT, element_code INTEGER, element TEXT, year INTEGER, period TEXT, unit TEXT, value DOUBLE, value_qualifier TEXT, flag TEXT, note TEXT, source_code INTEGER, source TEXT, file_date_update INTEGER`. Numeric items retain their integer code; alphanumeric items use `item_code_text` with `item_code: null`. Observation identity includes the exact item, period or annual year, and source where supplied, so multiple source estimates cannot overwrite one another. Indexes cover the code and year filters, with composites for common item/element/year queries. The area/year index is installed by the statistics worker before `ANALYZE`, never by synchronous store-open DDL. An existing mirror missing that index schedules the same background job even when statistics already exist; syncs await that job and refresh statistics after installation without re-downloading data. Shared dimension tables provide FTS5 over labels for `resolve_codes`. The ingester maps columns from each CSV header.

**Ingest upgrades.** Nullable columns are added to existing cubes without a per-row backfill. Compatible numeric annual domains retain their keys and readiness under revision 1; their item membership query uses only the existing numeric index until sync prepares the text indexes and promotes revision 2. Promotion precedes any compatible refresh writes so a failed refresh cannot hide newly written text identities. All of this preparation — the replacement delete, the new indexes, the promotion — runs as the first step of the sync generator, so only once the sync holds the store's sync lease: a sync another process's lease refuses (`sync_locked`) changes nothing. A replacement publishes revision 2 after its completion state commits and before it releases the lease. A compatible revision-1 cube can advance to revision 2 before ingestion begins, once index preparation has finished without cancellation. FS and GLE have no ready revision until replacement completes: they must recover previously dropped rows and source collisions even when the upstream date is unchanged. Fresh cubes can install the indexes while empty. Sync-time preparation of populated cubes sends missing index DDL to the pool’s maintenance slot under the sync’s lease. The worker checks the owner and generation inside its write transaction, renews the lease on success, and the sync awaits that work before promoting the revision. Stopping a scheduled refresh waits for any index job already dispatched to settle before releasing the sync lease. The first read of an older populated mirror leaves index preparation to its next sync. Item dimensions use an internal rowid for FTS, while callers receive only the source's numeric or text identity.

The item vocabulary is repaired as part of the same first step: a sync adds every item identity the cube holds that the vocabulary lacks, labeled from its lowest-rowid row, so a mirror synced while FAO shipped a short or header-only item list gains the missing items on a refresh that downloads nothing. Store version 3 adds the planner-statistics stale flag, clear, so an upgrade alone schedules no build. Store version 4 adds the `file_date_update` column and clears each existing store's checkpoint, so the first refresh re-downloads every synced domain once, stamping the rows its file carries and removing the rest, while the domain stays ready. Store version 5 adds the statistics generation without invalidating existing statistics.

**Decision: a refresh removes rows by file stamp (#63).** The stamp belongs to the file, not the run, so a run stopped anywhere and rerun removes the same rows, and removals land only after every row of the file is in, so a read never sees a half-empty cube. Rejected: a per-run generation deleted in the completing transaction, a seen-set anti-join, a shadow-table swap, and a file-row-count heuristic.

**Element discovery.** Resolution returns distinct non-null units from the requested domain, optionally restricted to numeric or text item selections. The item scope applies before exact, full-text, substring, and paged matching. Empty explicit selectors match nothing. Domain-wide discovery uses a covering `(unit, element_code)` index installed during sync; leading with unit keeps it from competing with observation reads that need element/year order. Old mirrors use a sequential scan until refresh prepares the index. An empty observation query with explicit items and elements returns `available_elements` for those items across the domain, without claiming coverage for its area, year, or source filters.

**Item groups.** Read-time classification marks verified domain-specific groups as `aggregate`. The curated set covers QCL (1717, 1720, 1723, 1730, 1735, 1738, 1780), TCL (1723), and 24 FBS groups and totals (2901, 2903, 2905, 2907, 2908, 2909, 2911, 2912, 2913, 2914, 2918, 2919, 2922, 2923, 2924, 2928, 2941, 2943, 2945, 2946, 2948, 2949, 2960, 2961). The FBS set uses FAO’s `CBDstep2.lst` and `CBDstep3.lst`, cross-checked against the FBS data rows. `kind: null` leaves group membership unknown. The classification is available on existing mirrors and does not change which observations queries include.

**Search and identity inputs.** `faostat_resolve_codes` reads `query`, and `faostat_commodity_profile` reads `item_query`, by one rule whenever no exact selector wins (#67). A blank or `*` value reads as omitted, which lists on the resolver and fails `missing_item` on the profile; a value made only of quotes, parentheses, asterisks, and whitespace fails `invalid_query`, so the caller learns its query never ran; anything else searches. Quotes, parentheses, asterisks, and control characters separate words. Each distinct word is searched once, in groups of at most 64 terms per FTS5 statement that a row must all match, so search time is linear in the query's length. A query that leaves no word the index holds matches nothing and never falls through to the substring filter or the listing. The query and `name_contains` text that notices and error messages name is JSON-quoted with control characters escaped. Text item identities are stored uppercase, so `code_text` and `item_codes_text` are uppercased before any read (#68). Area matches carry FAO's `m49_code`, a string with leading zeros; `m49_code` looks areas up exactly, zero-padding the integer part to three digits, and returns every area carrying the code on one page, because nothing in the schema keeps a code to one area. It takes precedence over `query` and `name_contains`, and is rejected beside `code` or `code_text` or outside the area dimension as `invalid_m49_selector` (#65). The codes are FAO's: some areas carry dotted extensions, so they do not map one-to-one to ISO numeric codes.

**Off-thread reads (`ReadPool`).** Both SQLite drivers execute statements synchronously. Two `node:worker_threads` workers serve cube reads and the dimension store’s text search, including normalized exact-label preference and FTS5. The resolver and profile pass the same per-call signal to the text search that they use for their cube reads. Exact-code lookup, substring filters and listings use the existing dimension-store path. The main thread owns the framework `Mirror` and initializes each database before dispatching work. Each worker opens its own SQLite handle for a job’s file and keeps the shared dimension database handle query-only. Workers spawn on first use and do not keep the process alive while idle. Closing the pool rejects queued and running jobs with `pool_closed`, closes idle handles, and retires busy workers.

- **Per-call ceiling.** A tool call takes one signal from `FaostatMirror.readSignal()` before its first read: the call's own signal plus a 45 s ceiling (`QUERY_CEILING_MS`), which sits under the MCP SDK's 60 s default client timeout and covers queue wait and execution across every read the call makes. Past it, the read fails with a retryable `Timeout` carrying `reason: 'query_timeout'`. `faostat_query_observations`, `faostat_commodity_profile`, and `faostat_resolve_codes` declare that reason with their own recovery. A cancelled call settles as `RequestCancelled`. A read failure raised inside the staging stream (ceiling, cancellation, crashed worker) fails the call rather than falling back to an inline page.
- **Cut-off and retirement.** When the signal aborts, the caller is rejected at once. A queued read just leaves the queue. A running read cannot be stopped, since `worker.terminate()` takes effect only once the statement returns, so its worker is retired and a replacement serves the next job. Retired workers count toward a four-thread cap: a replacement spawns only while live plus retired workers number fewer than four, and at the cap a job with no free live worker waits in the queue for a retired worker to exit, so the pool never holds more than four threads. A worker that crashes fails its job with a retryable `ServiceUnavailable` and is respawned for the next.
- **Handle epochs.** Workers reopen a file when their handle’s epoch is stale. A committed statistics build increments `planner_statistics.generation` in the same transaction that clears `stale`. The server checks that state on the reads that need these statistics and bumps the local epoch when it detects another process’s generation, so workers pick up the committed plan without a restart.
- **Opening behind a lock.** A worker's open waits out another connection's lock — such as one recovering the WAL index after workers are retired and respawned — for up to the handle's 5 s `busy_timeout`: `openSqliteHandle` sets `busy_timeout` before its first read of the file and retries the switch to WAL itself ([cyanheads/mcp-ts-core#607](https://github.com/cyanheads/mcp-ts-core/issues/607)). An open that still fails rejects the read as `DatabaseError`, the driver's error on `cause`.

**Query-planner statistics.** Without `sqlite_stat1`, SQLite can choose an element/year index for an item/element/year filter and scan the whole element slice. The mirror builds statistics when rows have changed, statistics are missing, or a full index has no statistics. The sync marks `planner_statistics.stale` before committing pages that change rows and in the transaction that clears a cube for replacement. The worker runs one `ANALYZE` per index in one transaction and publishes the new generation with the statistics. It prepares the area/year index in a separate transaction first when needed. Sampled `ANALYZE` was rejected because its uniform per-key estimates left the wrong index selected.

Reads that find missing or stale statistics schedule a background build and go ahead on the available plan. The pool gives maintenance one slot and prioritizes queued reads. Reads defer a build while a sync or its closing build holds the domain lease. The worker rechecks the lease and the expected statistics generation under its write lock, so a queued build can yield to a sync or a newer committed build without recording a failure.

An in-process sync waits for a build of the same domain already in flight. After the sync releases its lease, it awaits a closing build if statistics are stale or incomplete. That worker claims the same store lease under its own owner. While it holds the lease, other processes can continue reading, and competing syncs and statistics builds defer. If another process claims the lease first or has already committed the needed statistics, the closing job yields. A killed worker can leave its lease until the two-minute expiry, during which reads continue. Cancelling a sync stops its wait for statistics. Pool shutdown ends the worker after its current statement, and an uncommitted statistics transaction rolls back.

**Decision: a statistics build is a run of per-index `ANALYZE` statements, run on the pool's worker (#62).** `worker.terminate()` takes effect only once the running statement returns, and under Node process exit waits for it, so a single whole-table `ANALYZE` could hold shutdown for the whole of it; one `ANALYZE` per index bounds that wait to one index's statement. A child process for the build was rejected: the launch binary is unverified inside the `.mcpb` bundle, a hard kill would orphan it, and it adds an IPC and test surface.

The read-side trigger sits on the reads the statistics serve — the filtering and aggregating paths — and not on `resolve_codes`'s distinct-item-code read (`domainItemCodes`): a loose index scan that seeks the `item_code` index, and the partial `item_code_text` one, once per distinct code, independent of planner statistics. That call, the one an agent makes first, would spend a worker on an optimization it cannot use (#22), and every sync's item-vocabulary repair runs the same read while a build is pending. Statistics are an optimization, so a failed build (read-only volume, a writer holding the lock past `busy_timeout`) leaves the domain planning from the statistics already in place, or without any, rather than failing anything, and only success is remembered. A later data read retries, so contention that clears costs one more build rather than the old plan for the rest of the process. Reads stop retrying after three failed attempts per domain per process, so an obstruction that never clears cannot re-run a minute-long pass on every request; a later sync still builds. A build the pool's shutdown ends — queued, running, or asked of the closed pool — counts as neither: it logs no warning and spends no attempt (#46).

**Row-read ordering.** The two row reads — the page read behind `faostat_query_observations` (one row past `limit` at `offset`) and the spill stream both staging tools use — return rows in year order and prepare one statement, built by `buildObservationSql`. Without an item filter they `ORDER BY year`, so `(element_code, year)` or `(year)` supplies the order and the `LIMIT` stops the scan early. With an item filter they `ORDER BY +year`: the unary plus stops the planner from choosing an index just to avoid the sort, so it seeks `(item_code, element_code, year)` and sorts the matched rows, which the item codes already bound. Under a plain `year` and the spill stream's 50,001-row `LIMIT`, `bun:sqlite` (the Docker runtime) chose the `(element_code, year)` order instead and walked the whole element slice, testing `item_code` per row — on `QCL`, 1.6M rows to return 27,893 for the five items "sugar" resolves to (#33). `rowid` breaks ties within a year (`ORDER BY year, rowid` / `+year, rowid`), so the order is total and the same under every index the planner can pick: a page walk whose plan changes between calls neither repeats nor skips a row (#52). It changes no plan — `rowid` is the implicit suffix of every index. A page that overflows without staging counts the match with `countObservations`, which reads at most 50,001 rows, so `totalCount` is exact up to 50,000 and a floor beyond, disclosed by `totalCountIsFloor`. `offset` is bounded at 100,000 (`OFFSET_CAP`), so offset paging reaches the first 100,000 rows of a match plus one page; the schema rejects a larger `offset`, and a page whose next page would start past the bound omits `nextOffset` while its notice says to partition the query by year or narrower codes. The bound is twice the staging cap, so the rows past a truncated staged table stay reachable by `offset`.

**Resilience.** Both bulk fetches use the raw `fetch` (a `fetchWithTimeout` deadline would also cover the body stream of a multi-hundred-MB ZIP) and map a non-2xx response through `httpErrorFromResponse`, so the status sets the error code: 403 → `Forbidden`, 404 → `NotFound`, 408/425/504 → `Timeout`, 429 → `RateLimited`, other 5xx → `ServiceUnavailable`. The manifest fetch runs inside `withRetry` (base delay 1.5 s, three retries — the service is occasionally slow or degraded), so only a transient status (408, 425, 429, 5xx other than 501) re-enters the backoff; any other status fails on its first request. The FAO bulk host answers a wrong path with 403, so a manifest failure that will not be retried carries a recovery hint naming `FAOSTAT_BULK_BASE_URL` (in the hint, never the message), which `faostat_list_domains` and the `mirror:init` / `mirror:refresh` scripts all show. The per-domain ZIP download is not retried in-process; its status error names the domain and keeps the ZIP URL on `error.data`, since it reaches only the sync logs. Parse failures on a malformed ZIP throw transient errors, not `SerializationError`, so a refresh retries.

**CLI refresh contention.** The one-shot `mirror:refresh` retries `sync_locked` and SQLite busy on the pre-claim store open. Each domain has a two-minute retry window that includes the time spent trying to acquire the store and lease. A native SQLite call already in progress can finish its bounded lock wait. After the window expires, the CLI skips that domain and proceeds, then exits nonzero with the skipped codes. Cancellation stops a backoff wait immediately. An acquired lease leaves the remainder of that sync under the caller’s signal. The HTTP cron skips `sync_locked` immediately and retries on its next run.

**Readiness.** Read path gates on `await mirror.ready()` per domain. Cold (never-completed init) → `faostat_query_observations` throws `index_not_ready` with a recovery hint to run the init or wait. Ordinary refreshes remain queryable. An incompatible ingest revision makes the affected domain unready until its replacement sync completes, including after an interrupted replacement.

| `CANVAS_PROVIDER_TYPE` | no | DataCanvas engine. `src/index.ts` defaults it to `duckdb`; `none` turns the SQL surface off, the `dataframe_*` tools then report `canvas_disabled`, and `faostat_query_observations` pages with `offset` and stages nothing. |
| `CANVAS_DEFAULT_ROW_LIMIT` | no | Most rows one `faostat_dataframe_query` call returns, and the cap its `row_limit` is served at; below 1000 it is also `row_limit`'s default. A core var. Default `10000`. |
| `FAOSTAT_DATAFRAME_DROP_ENABLED` | no | `true` makes `faostat_dataframe_drop` callable. Default `false`: the tool is registered disabled (absent from `tools/list`, shown on the landing page with the enable hint), and the server `instructions` omit it. |
| `FAOSTAT_CLAMP_LIMITS` | no | A count input (`limit`, `top_n`, `row_limit`) above its cap is served at the cap, with `requestedX` / `effectiveX` fields and a notice. `false` advertises each cap as a schema maximum and rejects larger values. Default `true`. |

Server config lives in `src/config/server-config.ts` as a separate Zod schema (`parseEnvConfig`), never merged with core config. `CANVAS_PROVIDER_TYPE` and `CANVAS_DEFAULT_ROW_LIMIT` are core vars (already in `AppConfig`); the rest are server-specific.

Peer deps to add: `@duckdb/node-api` (DataCanvas), and on Node deployments `better-sqlite3` (MirrorService — `bun:sqlite` is built-in on Bun). Mirror + canvas are both Node/Bun-only (no Workers build); this server does not target Workers.

## Implementation Order

1. **Config + server setup** — `server-config.ts` (domain list, paths, base URL), `createApp({ name: 'faostat-mcp-server', title: 'faostat-mcp-server', … })`, canvas accessor wired in `setup()`.
2. **Mirror service** — `defineMirror` + `sqliteMirrorStore` per domain, the bulk-ZIP `sync` ingester (manifest fetch → stream-parse code lists + data CSV), shared dimension tables, FTS index. `runSync` CLI scripts (`mirror:init`, `mirror:refresh`, `mirror:verify`); refresh cron in `setup()` (`ScheduledRefresh`: a domain another process is syncing is skipped; `teardown()` stops a run in flight).
3. **`faostat_list_domains`** — live manifest read + per-domain mirror status. (Independently testable against the manifest.)
4. **`faostat_resolve_codes`** — FTS5 / filter over dimension tables; country-vs-aggregate classification.
5. **`faostat_query_observations`** — mirror query with code/year filters + aggregate exclusion; paging with `offset`, staging to canvas on overflow.
6. **`faostat_dataframe_describe` + `faostat_dataframe_query`** — canvas introspection + read-only SQL (mandatory pair for the spilled `canvas_id`).
7. **`faostat_commodity_profile`** — workflow composing `resolve_codes` + production/trade mirror queries.

Each step independently testable. Tools 3–5 can land before 6–7; the mirror (step 2) gates everything.

## Workflow Analysis

`faostat_commodity_profile` (multi-step, mirror-internal — no external calls per request once indexed):

| # | Operation | Source | Purpose |
|:--|:----------|:-------|:--------|
| 1 | Select one QCL `item_code`, or resolve `item_query` | Complete QCL vocabulary: normalized exact label first, otherwise unique FTS match | `item_code: 56` → Maize (corn); ambiguous queries return candidates and resolve-then-select guidance |
| 2 | Top producers | `QCL` mirror table, element Production, or the item's Stocks elements (#51), `SUM(value)` GROUP BY `(area_code, unit)` at each group's own `MAX(year)`, ORDER BY the sum | Ranked producer list (countries only, aggregates excluded) |
| 3 | Annual trend | `QCL`, every matching area, `SUM(value)` GROUP BY `(year, unit)` over all years in range | Year/value series inlined in the response |
| 4 | Trade flows | `TCL` mirror table, Import/Export quantity of the trade item (the selected item, or `trade_item_code`; tonnes for a selected item with Production, otherwise every quantity element the trade item carries), same per-area aggregation as step 2 | Top importers/exporters |
| 5 | Stage full set on canvas | `spillover()` → canvas table | Escape hatch for `faostat_dataframe_query` |

Design questions the table surfaces: the profile runs up to 4 mirror aggregations (production rank, trend, export rank, import rank), picks their elements with two item-scoped element reads (`itemElements`, index-only, one per domain), names each ranking's units with up to two `elementUnits` reads (one per domain), and merges them; it inlines a compact summary (top-N + the annual trend) and spills the row-level union to one canvas table so the agent can drill in. Steps 2–4 aggregate in SQL over the complete filtered match rather than over a row-oriented page, so a ranking is bounded by neither the staging cap nor the read path's `ORDER BY year ASC` ordering. An aggregate cannot use a `LIMIT` to bound its own input the way a row fetch can, so these are the queries most exposed to a bad index choice — they are the reason the cube's query-planner statistics (above) are maintained rather than left to chance. No elicit (read-only, idempotent). If the trade domain (`TCL`) isn't indexed, the profile returns a result without trade, with a `notice` naming the gap, rather than failing — production without trade is still useful. Production is the backbone: an unselected `QCL` fails with `domain_not_indexed`, a selected but cold one with `index_not_ready`.

**Selection and ranking semantics.** The profile selects exactly one QCL item: distinct products sharing a unit are not additive. Explicit `item_code` takes precedence and must be present in QCL. Query-only calls compare trimmed, whitespace-collapsed, case-folded labels, with `;` and `,` compared alike (FAO writes `Peas; dry` where callers write `Peas, dry`), across the complete QCL vocabulary before FTS; multiple candidates require explicit selection rather than a primary-item guess. Each `(area, unit)` group is taken at its *own* latest year with data, so a fast-reporting country's newest year does not drop slower reporters. Grouping by `unit` keeps tonnes and head counts apart; with one unit there is one row per country.

The profile picks its elements from what the item carries (#51), read once per domain from the item's own rows and independent of the year bounds, so the bounds never switch an item between elements. In QCL the producer ranking and trend use Production (5510) when the item has any Production row, otherwise every Stocks element it carries (5111, 5112, 5114 — the live-animal items); in TCL an item with Production keeps the tonne quantities (5610 imports, 5910 exports), and any other item ranks every import (5607–5610) and export (5907–5910) quantity element it carries, grouped by unit. `ranking_elements` names each ranking's elements and units, and the `format()` headings carry them. An item with no applicable element returns empty sections with a notice. A crop traded mostly in processed form has no trade under its own item (QCL paddy rice 27; its trade sits in TCL's rice milled equivalent 30), so an optional `trade_item_code` names the TCL item `top_exporters`, `top_importers`, their units, and the staged TCL rows read, while producers, the trend, and the element choice stay on the selected item. The TCL element read for the code doubles as the check that it names a TCL item with rows, failing as `trade_item_not_found` before any ranking read, and `trade_item: { code, name }` echoes it when TCL is indexed and has finished its initial sync; while TCL is unselected or has no completed sync, the code goes unchecked and the no-trade notice stands. When neither trade ranking has an element, the notice points to `faostat_resolve_codes` on TCL and `trade_item_code`; when a `trade_item_code` naming another item was supplied it names the TCL elements that item does carry instead, taken from that same element read, and asks for a `trade_item_code` whose item carries the quantity elements, or for none. A `trade_item_code` equal to `item_code` reads in the notice as if omitted. Units are checked per item, so a head-count Stocks item beside a tonne trade item is not reported as one item in two units. Every ranked row carries an integer `years_behind` (#50): its ranking's latest year minus its own year, 0 when current, computed in the ranking's own single read as `MAX(year) OVER () - year`. No row is excluded or reordered; the notice names each returned lagging row with a `year_start` that drops it. Each ranking is one item-bounded read — each area and unit at its own latest year through a window over the matched rows, with no self-join.

## Design Decisions

**Data path — bulk CSV, not REST (verified 2026-06-13).** Every `faostatservices.fao.org/api/v1/` endpoint (`/data`, `/domains`, `/definitions`, `/codes`, `/dimensions`) returns `HTTP 401 "Missing Authorization Header"` keyless, with default and browser UA; the legacy `fenixservices` host times out. The bulk service (`bulks-faostat.fao.org/production/datasets_E.json` + per-domain ZIPs) is HTTP 200, keyless, and machine-readable (68 datasets with size, row count, update date, and exact ZIP URL). Each ZIP bundles the data CSV **and its dimension code lists**, so the bulk path supplies both the cube and the vocabularies — no API needed. Full probe log: `docs/data-source-verification.md`. **Decision: build entirely on the bulk service; do not implement a REST client.** If FAO restores keyless REST later, it could back a live fallback for un-indexed domains — noted, not built.

**Storage backend — MirrorService (embedded SQLite + FTS5).** Corpus sizing decides the tier per the framework's guidance (in-memory ≲10⁴; MirrorService 10⁴–10⁷; external ≳10⁸). The full corpus is ~170M rows / 1.48 GB compressed, but it's skewed: trade matrices dominate (`TM` 52M, `TCL` 17M) while the core analytical domains are 10⁴–10⁷ each (`QCL` 4.2M, `FBS` 4.8M, `GLE` 6.7M, `RL` 0.41M). In-memory is wrong (4.2M QCL rows won't fit comfortably and vanish on restart); an external store is overkill for a single-process public-data server. MirrorService gives durable, cross-session, FTS-indexed local query with a self-refresh state machine — exactly the "mirror a bulk upstream instead of paginating it live" pattern. `TM` (52M) is deferred from the default set on size; it can be opted in via `FAOSTAT_DOMAINS` where the deployment has the disk/RAM.

`TCL` (17.3M rows, 271 MB compressed) slightly exceeds the 10⁷ guide — it is included in the default set because it shares the standard normalized cube schema, SQLite handles it well with the declared `(item_code, element_code, year)` indexes, and dropping it eliminates trade flows from the default commodity profile workflow. Deployments constrained on RAM or startup time can remove it from `FAOSTAT_DOMAINS`; the design's `domain_not_indexed` error path surfaces the gap clearly.

**DataCanvas — yes (both gates pass).** (1) *Analytical, not just large:* the workload is `SELECT element, area, year, SUM/AVG(value) … GROUP BY …` — cross-country comparison, multi-decade trends, producer rankings. An agent absolutely writes `GROUP BY` against this. (2) *Too big to inline:* a single area×item×element×year slice across 245 countries × 60+ years easily exceeds any context budget. So `faostat_query_observations` returns one page of up to `limit` rows (`offset`/`nextOffset` reach the rest up to the 100,000-row offset bound, canvas or not) and stages the full match to a canvas table on a first page whose match exceeds `limit`; `faostat_commodity_profile` inlines its summaries and stages the row-level set, and — per the framework's hard rule — the `canvas_id` is paired with `faostat_dataframe_query` (+ `faostat_dataframe_describe`) in the same surface. Without the query pair the token is dead output. The canvas carries only the *row-level* set: `faostat_commodity_profile`'s own pre-aggregated summaries — the top-N rankings and the per-year trend — are bounded by `top_n` and the domain's year span, so they inline unconditionally rather than depending on a canvas the deployment may have turned off. Mirror and canvas coexist with distinct lifecycles: **mirror** = durable, cross-session, refreshed on a schedule (the corpus); **canvas** = ephemeral, per-session, the agent's working slice spilled from a query. The session canvas is acquired through the framework's `acquireShared` (one canvas per tenant under concurrent first calls; replacing a dead one purges its staged-table records); `faostat_dataframe_describe` and `faostat_dataframe_drop` never mint a canvas. The staged table schema is **explicit**, not inferred: the codes and `year` are `BIGINT`, the labels, `unit`, and `flag` are `VARCHAR`, `value` is `DOUBLE`, `area_m49` is `VARCHAR` (the last observation column, after `source`, so leading zeros survive), and profile tables add `domain` (`VARCHAR`) after it. Inference would type each column from the rows already buffered under the staging helper's character budget, and rows stream oldest year first — a series whose early years are whole numbers would stage `value` as `BIGINT`, and DuckDB's appender would silently truncate every later fractional value.

**Why mirror *and* canvas, not canvas alone.** Canvas is per-session and in-memory — staging 4.2M QCL rows into a canvas on every cold session would re-download and re-parse a 33 MB ZIP each time. The mirror holds the corpus once, durably; the canvas holds only the *result* of a filtered query the agent wants to SQL further. The mirror answers "give me wheat production for India, 2000–2022" directly (indexed lookup); the canvas answers "now let me regroup and rank what came back" without another upstream hit.

**Code resolution as a dedicated tool, not a resource.** Name → opaque code is the dominant operation, alongside listing and filtering. Tool-only clients must reach it, so resolution is a tool backed by FTS5 over the bundled code lists in the mirror, with item identities the lists omit taken from the data rows. Its country-vs-aggregate classification lets the caller distinguish regional totals from their constituent countries.

**Aggregate exclusion default.** `faostat_query_observations` defaults `include_aggregates: false`. FAOSTAT puts World/continents/economic-groupings in the same `area` dimension as countries. The shared boundary excludes codes ≥5000 and curated rollups 261, 265, 266, 268, 269, 351 and 420 (EU trade blocs, China and Sub-Saharan Africa). Resolution classifies them at read time, so existing mirrors need no re-sync. Pages, streams, rankings and trends share this exclusion; explicit area codes or `include_aggregates: true` retain access. Historical reporting entities such as USSR and Yugoslav SFR remain countries.

**Surface kept tight (7 tools, one opt-in).** A standalone `faostat_get_sync_status` tool was considered and folded into `faostat_list_domains` (per-domain `indexed` / `row_count` / `last_update` fields) — one tool answers both "what exists" and "what's queryable." `TM`-specific tooling, prices, and population domains are reachable via the generic cube tools once indexed; no per-domain tools.

## Known Limitations

- **Mirror freshness lags FAO.** Data is as fresh as the last successful sync (`DateUpdate` per domain, surfaced in `list_domains`). FAOSTAT updates domains a few times a year, so a daily refresh is far more than enough — but a query reflects the mirror, not a live read.
- **Indexed subset.** Only domains in `FAOSTAT_DOMAINS` are queryable; `list_domains` shows the full catalog so the gap is visible. Expanding the set requires a re-sync (and disk/RAM for large domains like `TM`).
- **No sub-national data.** FAOSTAT is country-level (plus regional aggregates); no province/state granularity. For US sub-national, compose with `usda-mcp-server`; for EU, `eurostat-mcp-server`.
- **Imputed/estimated values.** A meaningful share of cells are flagged `E`/`I` (estimated/imputed). Flags are carried on every row; downstream rigor depends on the agent honoring them.
- **Workers-incompatible.** MirrorService (SQLite) and DataCanvas (DuckDB) are both native; this server runs on Node/Bun only.
- **Node exit waits for a running statement.** Neither SQLite driver can interrupt a statement once it starts. Under Node (the npm bin and the `.mcpb` bundle), process exit waits for any statement a read worker is still running, such as a read cut off at the ceiling or the one statement of an in-flight statistics build: one index's `ANALYZE`, the area/year `CREATE INDEX` on a store that lacks it, or the opening `BEGIN IMMEDIATE` waiting up to the 5 s `busy_timeout` for another connection's write lock. That build commits no statistics, and the next process builds again. On the largest cube one statement can still outlast the framework's 10 s backstop. Under Bun (the Docker image), the process exits at once.
- **MCPB bundle.** The Claude Desktop extension uses stdio with DataCanvas disabled. The bundle cleaner strips platform-specific DuckDB bindings. The DataCanvas query and describe tools remain listed and return `canvas_disabled`.

## API Reference

- **Manifest:** `GET {FAOSTAT_BULK_BASE_URL}/datasets_E.json` → `{ Datasets: { "-xmlns:xsi": "…", Dataset: [{ DatasetCode, DatasetName, Topic, DatasetDescription, Contact, Email, DateUpdate, CompressionFormat, FileType, FileSize, FileRows, FileLocation }] } }`. Lowercase filename is canonical (capitalized variant → 403). The `"-xmlns:xsi"` sibling key in `Datasets` is an XML-to-JSON artifact — access `d.Datasets.Dataset` directly; the key name contains a `-` so object-spread patterns skip it safely. `FileSize` is a string with units (`"33127KB"`, not a number). All 12 per-dataset fields listed above are present on every entry.
- **Domain ZIP:** `FileLocation` URL, e.g. `…/Production_Crops_Livestock_E_All_Data_(Normalized).zip`. `accept-ranges: bytes`, `last-modified` present. Bundles: `<Name>_E_All_Data_(Normalized).csv` (data) + `<Name>_E_AreaCodes.csv`, `<Name>_E_ItemCodes.csv`, `<Name>_E_Elements.csv`, `<Name>_E_Flags.csv` (dimension code lists). Survey-shaped domains bundle different dimension files (e.g. `_Surveys.csv`, `_Indicators.csv`).
- **Normalized data CSV columns (standard cube):** `Area Code, Area Code (M49), Area, Item Code, Item, Element Code, Element, Year Code, Year, Unit, Value, Flag, Note` (13 columns). Calendar-year domains duplicate `Year` in `Year Code`. FS also has period labels such as `2000-2002`: retain the label as `period` and derive `year: 2001` for range filtering; its concatenated `Year Code` is not a calendar year. Preserve alphanumeric item codes in `item_code_text` with numeric `item_code: null`. A censored value such as `<2.5` becomes `value: 2.5` with `value_qualifier: "<"`. GLE adds `Source Code` and `Source`, retained as separate observation dimensions. `Area Code (M49)` carries a leading apostrophe (`'004` for Afghanistan), stripped when normalizing the M49 code. `Note` is frequently empty.
- **AreaCodes CSV:** `Area Code, M49 Code, Area` (note: space after comma in header — parse as CSV, not by char position). Contains countries, historical reporting entities and aggregate regions. World=5000, Africa=5100, continents `51xx`–`56xx`, economic groupings, plus excluded-intra-trade variants with a trailing-zero code (`51000` = "Africa (excluding intra-trade)"). Codes below 5000 also contain rollups; use the shared aggregate boundary above rather than the threshold alone.
- **Flags CSV:** `Flag, Description`. `A` Official figure · `B` Time-series break · `E` Estimated value · `I` Imputed by receiving agency · `X` External-org figure (full set in each domain's `_Flags.csv` — parse it at sync time; don't hardcode).
- **ItemCodes CSV:** `Item Code, CPC Code, Item`. `CPC Code` carries a `'` prefix (e.g. `'F3102`) — strip the apostrophe if storing raw CPC for crosswalks. Some domains ship the list short or header-only, so the items the data rows name that the list lacks are added with their rows' labels and no CPC code.
- **Elements CSV:** `Element Code, Element` (two columns only).
- **Compression ratio ~18×.** Stream-parse from the ZIP; never decompress the full CSV to memory.
