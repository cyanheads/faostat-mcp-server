# 0.2.1 — 2026-07-27

## Fixed

- **`faostat_query_observations` honors `limit` on mid-size matches.** A result between the 50-row overflow probe and the ~100,000-character staging budget previously ignored `limit` and returned every matching row inline. The inline page is now capped at `limit`; a match larger than `limit` stages in full to a canvas table (`canvas_id` + `table_name`) so the rows past the page stay reachable through `faostat_dataframe_query`, and when staging itself fails the notice discloses the shortfall instead of a capped page reporting itself as the exact, complete result. ([#14](https://github.com/cyanheads/faostat-mcp-server/issues/14))
- **Query-planner statistics for the mirror's per-domain SQLite tables.** With no `sqlite_stat1`, SQLite's cost-based optimizer couldn't compare the composite indexes and picked the less selective one for the item+element filter shape `faostat_commodity_profile`'s ranking and trend aggregates use — measured on the real mirror at roughly 1,190 ms vs 6 ms for the equivalent year-scoped query. `ANALYZE` now runs against a domain's cube table lazily on first read (so a mirror synced before this existed is caught up without a re-sync) and again after any sync applies rows (a domain ZIP replaces the vintage the prior statistics described). Partially addresses [#3](https://github.com/cyanheads/faostat-mcp-server/issues/3) — its synchronous, main-thread `bun:sqlite` execution remains open.
