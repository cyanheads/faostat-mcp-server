# 0.3.0 — 2026-10-03

## Added

- **`faostat_dataframe_drop`** drops one staged canvas table, with its provenance, before its 2-hour TTL. Idempotent: a name that isn't staged returns `dropped: false` with a notice. Declared errors: `canvas_disabled`, `canvas_not_found`.
- **`FAOSTAT_DATAFRAME_DROP_ENABLED`** (default `false`) opts in to `faostat_dataframe_drop`. While off, the tool is registered disabled: absent from `tools/list`, shown with its enable hint on the HTTP landing page, and not named in the server instructions.

## Changed

- **`ctx.log` client notifications honor `MCP_LOG_LEVEL`** ([cyanheads/mcp-ts-core#621](https://github.com/cyanheads/mcp-ts-core/issues/621)). With `warning`, the info-level `notifications/message` are no longer sent, and a client's `logging/setLevel` can only narrow that floor; before mcp-ts-core 0.13.11 they were sent regardless of `MCP_LOG_LEVEL`.
- **The mirror read worker's own `SQLITE_BUSY` open retry is removed** ([cyanheads/mcp-ts-core#607](https://github.com/cyanheads/mcp-ts-core/issues/607)). `openSqliteHandle` now sets `busy_timeout` before its first read and retries the WAL switch itself, so an open behind another connection's lock still waits it out; a store that cannot be opened now fails the call as `DatabaseError`.
- **`server.json` npm entries** drop the `run start:stdio` / `run start:http` package arguments and use `runtimeHint: "npx"`. The `streamable-http` entry fixes `MCP_TRANSPORT_TYPE` to `"http"`, so a registry client launching it starts the HTTP transport ([cyanheads/mcp-ts-core#622](https://github.com/cyanheads/mcp-ts-core/issues/622)).
- **Docker image** — the `deps` stage runs `scripts/prune-musl-packages.ts`, removing DuckDB's musl binding (`@duckdb/node-bindings-linux-<arch>-musl`), which the glibc runtime never loads ([cyanheads/mcp-ts-core#608](https://github.com/cyanheads/mcp-ts-core/issues/608)). The build-stage install gains a BuildKit cache mount.
- **Repo upkeep** — `.gitignore` ignores every `.env*` file except the templates, and `.dockerignore` excludes every `.env*` file plus the MCP registry token files; the CodeQL workflow runs one job per language; the `.env.example` framework block matches the template; `CONTRIBUTING` takes contributions as issues; framework skills and scripts are synced from mcp-ts-core 0.13.11.
